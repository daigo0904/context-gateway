# 文脈ゲートウェイ

3L-HCCG v0.4（3層階層型コンテキスト制御ゲートウェイ）の共通基盤。

qwc / OpenClaw / voice-ai / Omnical が後から乗れる形の独立した部品として作る。

---

## これは何をするものか

長い会話を続けると、モデルへの入力（文脈）がどんどん膨らむ。膨らむと、
保存しておいたプロンプトが枠から押し出されて、毎回いちばん最初から
読み直すことになる。これが「だんだん遅くなる」の正体。

対策として文脈を削ると、今度は別の問題が起きる。**モデルは削られたことを知らない**ので、
足りない情報のまま平気で答えを返す。しかも誰も気づけない。

そこでこの部品は、削る代わりに次のようにする。

1. **受け取った文章は、まず全部ディスクに書く**（原文ストア）
2. **消しても情報が減らない部分だけを落とす**（出力側の独り言、あいさつ）
3. **本当に詰まっているのかを測る**（監視）
4. 詰まっていることが確認できてから、はじめて文脈を追い出す（未実装）

3 と 4 の順序が肝で、「圧縮が要る」という前提そのものを先に確かめてから作る。

## 使い方

### 他の道具から使う

```js
import { Gateway } from '/Users/daigo/文脈ゲートウェイ/index.mjs';

const gw = new Gateway();

// 1. 利用者の入力は、何よりも先に保存する
const u = gw.recordUserTurn('daigo', 入力文);

// 2. モデルを呼ぶ。出力の原文も保存する
const a = gw.recordAssistantTurn('gemma4:26b', 出力原文, u.record_id);

// 3. 画面に出すぶんだけ整える。原文は消えない
const 見せる文 = gw.filter(出力原文);
```

逐次出力（ストリーミング）のとき：

```js
const m = gw.stream();
for await (const chunk of ストリーム) process.stdout.write(m.push(chunk));
process.stdout.write(m.end());
```

**順序が大事**。入力を保存する前にフィルタをかけると、フィルタが情報を落とした時点で
原文が消える。`Gateway` はその順序を守りやすくするためだけに置いてある。

### 監視する

```
node bin/gw-monitor.mjs            # 1秒ごとに状態を表示・記録する
node bin/gw-monitor.mjs --judge    # 判定も一緒に表示する（それでも何もしない）
node bin/gw-monitor.mjs --quiet --out 記録.jsonl
```

止めるのは Ctrl-C。記録は `計測の記録/監視/` に日時の名前で残る。

```
node bin/gw-report.mjs 計測の記録/監視/xxx.jsonl   # 記録を集計する
```

### 原文ストアを手で見る

```
node bin/gw-corpus.mjs tail 20
node bin/gw-corpus.mjs get <record_id>
node bin/gw-corpus.mjs lineage <record_id>   # 要約から原文までたどる
node bin/gw-corpus.mjs stats
```

### 試験

```
npm test        # 45件
```

## 検証の状態

試験が通ることと、実物に効くことは別。**実機に当てて確かめたものと、まだのものを分ける。**

### 実機で確かめた

| 事柄 | 結果 |
|---|---|
| `/slots` が llama-server 直で取れる | 取れる（ポートは `ps` から。実測 51190） |
| プール圧がログから読める | 読める。内訳の合計が cache state の合計と一致（6210.4 = 6210.413） |
| decode の位相判定と tok/s | 87標本、33.9〜39.0 tok/s、基準 37.96 |
| prefill の位相判定 | 13標本、636〜850 tok/s（200ms間隔なら捕まる） |
| キャッシュ命中率が 0 以外になる | なる。同じ入力の2回目で **89.2%**。所要 7.81秒 → 2.29秒 |
| 状態サイズの式 | ログ17点で誤差 0.002 MiB |

### 実機に当てたら効かなかった

**口（出力フィルタ）は、gemma4:26b の実際の出力に対して 0.00% しか削らない。**

```
入力 2519 → 出力 2519 文字   think 0 / あいさつ 0 / 空行 0
```

理由は3つとも作った側の想定違い。

1. gemma4 の考え中の文章は `thinking` という**別のフィールド**で返る（本文2519字に対して5181字）。
   本文に `<think>` は入らない
2. qwc は `agent.mjs:132` で `delete m.thinking` を既にやっている。上流で二重に済んでいる
3. 「承知しました」「以下のコードをご覧ください」は実際の出力に現れなかった。
   あの正規表現は実物を見ずに書いたもの

45件の試験が通っていたのは、**試験の入力を自分の想定に合わせて書いたから**。
口を残すなら、狙う場所は本文ではなく `thinking`（本文の2倍ある）のほう。

### まだ確かめていない

- **プール圧が上がると遅くなるか**（§9 手順4 の本題。これが未実施なので手順6以降は作らない）
- 原文ストアへの同時書き込みで行が壊れないこと
- ログに複数のモデルが混ざったときの見分け（`sha256-06507c…` が混入した記録がある）

## 監視が見ている2つの数字

**どちらか片方だけでは足りない。** これは実機で確かめた結果、仕様の想定と違っていた点。

### 系統A `/slots`（llama-server に直接聞く）

ollama の窓口（11434）は `/slots` を持っていないが、ollama が内部で起動している
llama-server のポートを直接叩くと 200 で返る。**ポートは起動のたびに変わる**ので、
毎回 `ps` から引き直している。

ここから取れるのは、いま処理中の会話の文脈使用量と、
**プロンプトキャッシュの命中率**（`n_prompt_tokens_cache / n_prompt_tokens`）。
命中率が直接測れるので、仕様 §9 手順4 が想定していた間接測定（速度低下との時間的な一致を見る）
より強い材料になる。

### 系統B ログの `cache state` 行

```
srv update: - cache state: 20 prompts, 5714.027 MiB (limits: 8192.000 MiB, 65536 tokens, ...)
```

実際に詰まっているのはこちら。保存プロンプトの合計が 8192 MiB の枠を超えると
古い会話が押し出され、`forcing full prompt re-processing`（最初から読み直し）になる。

**`/slots` だけを見る実装は、枠が溢れている最中でも「圧力なし」と答える。**
仕様 §7.5 が名指しで警告している「安全機構が動作しないまま、動作しているように見える」
状態そのもの。だから2系統を必須にしている。

### この行は定期的には出ない（2026-09-05 実測）

`cache state` はリクエストの切れ目でキャッシュを更新したときにしか出ない。
92秒の生成中、一度も出なかった。つまり**プール圧は1Hzでは追えない。**

- 系統A `/slots` … 生成中も動く（`n_prompt_tokens` が 17→70→108→…と伸びる）。1Hz が要る
- 系統B プール圧 … リクエストの切れ目でしか動かない。イベントとして拾うもの

仕様 §6.2 の「1Hzで生成中も継続」が当てはまるのは系統Aだけ。
同じ値を1800回並べて「圧力は一定でした」と報告しないよう、
`saveDelta`（いま1本保存された）を出来事として記録している。

弱点も書いておく。この行が出るのは ollama が llama-server を `--log-verbosity 4` で
起動しているため。ollama を更新すると消えうる。消えたときに「値0」ではなく
「取得失敗」になるよう作ってある。

## 保存プロンプト1件の大きさ（2026-09-05 ログ17点から導出）

```
状態サイズ [MiB] = min(トークン数, 1024) × 106.26 KiB  +  トークン数 × 10.637 KiB
                   ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~     ~~~~~~~~~~~~~~~~~~~~~~
                   SWA窓が埋まるまでの分（1024で頭打ち）    窓の外に伸びていく分
```

17トークンから 21,044トークンまでの17点すべてで**誤差 0.002 MiB**。

### 前の版は間違っていた

`106.262 + 10.64 KiB × トークン数` という式を使っていたが、これは 2,000トークン以上の
点だけで直線を引いたもので、切片 106.262 MiB を「トークン数によらない定数」と
読み違えていた。実際は定数ではない。

| トークン | 実測 | 前の式 | ずれ |
|---|---|---|---|
| 17 | 1.941 MiB | 106.4 | **+104.5** |
| 252 | 28.769 MiB | 108.9 | **+80.1** |
| 20,355 | 317.698 MiB | 317.8 | +0.07 |

大きいところでは両方合う。**だから大きい点だけ見ていると気づけない。**

106.262 ÷ 0.10626 = **1024.0 ちょうど**。この数字は測って出た謎の定数ではなく、
SWA窓（`n_swa=1024`）そのものの大きさだった。

### 効いてくる違い

- 1トークン目の値段は **116.9 KiB**、1025トークン目からは **10.6 KiB**。11倍違う
- 20,000トークンを**丸ごと追い出す**と 314 MiB 浮くが、**半分に縮める**だけなら 104 MiB
- 8 GiB の枠に入る本数は、1本1,000トークンなら71本、20,000トークンなら26本

「縮める」と「追い出す」は桁が違う。仕様 §1.3 が言う「追い出す」は、この機械では
窓の分（106 MiB）まで回収できるので正しい。ただし**縮めるだけでは窓の分は戻らない。**

## 次にやること：手順4の計測

**判定基準を先に書いておく**（走らせてから決めない）。

### やること

長時間タスク（30分以上、文脈が伸び続けるもの）を1回流し、その間ずっと監視を回す。

```
node bin/gw-monitor.mjs --out 計測の記録/監視/手順4-1回目.jsonl
```

### 判定

前提仮説は「保存プロンプトのプールが溢れると、生成が遅くなる」。

| 結果 | 結論 | 次 |
|---|---|---|
| `forcing` が発生し、その前後で decode の tok/s が落ちている | 仮説は正しい | 手順5（閾値を決める）へ |
| `forcing` は発生したが tok/s は落ちていない | 原因は別 | 圧縮機構は保留。原因を探し直す |
| `forcing` が発生しない | この使い方では詰まらない | 手順5〜6は作らない |

3つ目になった場合も、**同じ形で報告する。** 負けた結果を報告しないと次の判断ができない。

### 計測の前に守ること

- ollama は `-np 1` で待ち行列が1本。外部セッションが1つ走るだけで数百秒ずれる。
  計測中は他の qwc / OpenClaw / voice-ai を止める
- 計測アームの前に ollama を再起動し、`N prompts, X MiB` が空になったことを数字で確認する

## 9/3 の計測の扱い

`計測の記録/arms/` は 9/3 に qwc の履歴書き換え方式（none / every / new の3アーム）を
比べたときのもの。**Step C（3アーム×2ローテ）は破棄**した。

理由は、仕様 §4/§5 が履歴書き換え方式そのものを捨てる（参照渡しに変える）ので、
どの書き換え方が最悪かを知る意味が無くなったため。
前提の検証としては r1 の前処理時間（none 126秒 vs every 238秒）で足りている。

`計測の記録/arms/破棄/` に入っているものは汚染が判明したアーム。集計に混ぜないこと。
