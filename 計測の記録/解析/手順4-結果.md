# §9 手順4 の結果 — 「文脈が長いと遅くなるのか」

**答え: なる。前処理も生成も、両方が長さに応じて遅くなる。**

出典は 9/3 のアームログ（llama-server の生ログ、6本）。
新しく計測したのではなく、既にあった記録を読み直した。

---

### 前処理（prefill、再処理500tok以上の手のみ）

| 文脈 | 再処理tok | tok/s |
|---|---|---|
| 0〜4k | 14,515 | 660 |

**前処理は1トークンあたり 3.2倍 遅くなる。**

これは「キャッシュが外れたから」ではない。**キャッシュに当たった上で**、
1トークンを処理する速度そのものが落ちている。注意機構の当然の性質だが、
この機械での実測値がこれ。

r2-none は汚染が判明したアーム（集計に混ぜない）。

### every（毎ターン圧縮）で何が起きたか

- 送信トークンは **1,133,434 → 476,454（-58%）**。圧縮そのものは狙い通り効いている
- しかし再利用率が **96.4% → 71.2%** に落ち、再処理は **40,536 → 136,998（3.4倍）**
- 結果、前処理は **126.2秒 → 272.6秒（2.2倍）**

**トークンを半分以下にしてなお、前処理は倍増した。**

一方で生成は速くなっている（26.4 → 32.0 tok/s、+21%）。表1の通り、
文脈が短いほど生成は速いので、これは筋が通っている。

差し引き：生成で約50秒得して、前処理で約146秒損した。**約96秒の負け。**

## 3. 圧縮しない場合、前処理は何をしているか

r1-none の手ごとの内訳（抜粋）。

| 手 | 送信tok | 再処理tok | 前処理ms |
|---|---|---|---|
| 1 | 2,903 | 2,903 | 4,520 |
| 2 | 4,745 | 1,842 | 3,448 |
| 3 | 4,837 | 95 | 313 |
| 4 | 6,656 | 1,819 | 3,773 |
| 5 | 6,758 | 105 | 347 |
| … | | | |
| 55 | 28,270 | 95 | 597 |

**再処理トークン数 ≒ 前の手からの増分。** キャッシュは完璧に働いていて、
新しく足した分しか処理していない。28,270トークン送っていても、
増分が95トークンなら前処理は0.6秒で済む。

つまり **「送信トークンを減らす」ことに、前処理を速くする効果はほぼ無い。**
効くのは「**1手で足すトークンを減らす**」ほう。

## 4. 結論

打ち手は2つに分かれる。**性質が正反対なので、混ぜて語らないこと。**

### 追記時に減らす（freeze-on-write）— 両取り

道具出力の上限、失敗出力の上限、同じ中身を二度積まない、など。

- 前処理: 1手あたりの増分が減る → そのぶん速くなる
- 生成: 文脈が伸びにくくなる → 表1のぶん速いままでいられる
- キャッシュ: **一切壊さない**（末尾にしか触らないため）

**副作用が無い唯一の打ち手。**

### 後から履歴を書き換える — 取引

要約への差し替え、古い出力の短縮など。

- 生成: 速くなる（26.4 → 32.0 tok/s を実測）
- 前処理: 書き換えた位置から後ろのキャッシュが死ぬ
- **毎ターンやると必ず負ける**（実測 2.2倍の悪化）

閾値に達したとき1回だけなら、成立しうる。1回の出費（縮めた文脈のフル前処理）を、
その後の生成の速さで取り返せるかどうかの計算になる。

28k → 8k に縮めた場合の概算：
- 出費: 8,000tok を 490 tok/s で読み直す ≒ **16秒**
- 収入: 生成が 24.7 → 31.4 tok/s（+27%）。出力1,000トークンあたり **8.7秒**

**約1,800トークンの出力で元が取れる。** アームの実測では1手あたり約82トークンなので、
**22手ほど**。それより手前で会話が終わるなら、圧縮しないほうが速い。

qwc の既定は `compactAtRatio: 0.7`（32,768 × 0.7 = 22,937トークン）。
この計算に照らすと妥当な位置にある。下げる提案が出たら、
上の「22手で元が取れるか」で判断すればよい。
