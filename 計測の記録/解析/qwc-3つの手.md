出典は `~/.qwythos-code/sessions/*.json`（199セッション）。
**注意**: このファイルは圧縮**後**の履歴を保存している。道具出力の中身は短くされていることがある。
ただし `tool_calls`（どの道具をどの引数で呼んだか）は assistant メッセージ側にあり、
`compactToolOutputOnce` は `role==='tool'` しか触らないので、**呼び出しの構造は無傷**。
7セッションだけ `compact()` を通っていて前半が消えている。

## 1. 会話を短く切る — ○ 効く（実装した）

| 75% | 14,800 |

そして qwc はこれまで**文脈の長さを一度も画面に出していなかった**。
`estimateTokens` は圧縮の判定にしか使われていない。気づけないまま遅くなっていた。

edit_file 14% / search_files 9%。探索系 53% : 実行系 39%。

## 3. maxToolChars 4000 → 2000 — △ ほぼ引き分け。やらない

| | |
|---|---|
| 道具出力の中央 | **100字** |
| 2,000字を超えるもの | 106件 / 1,033件（**10%**） |
| 4,000字の上限で切られたもの | 29件 |
| 切られたあとに読み直した | **6件（21%）** |

収支：
- 得 = 2,000字 ≒ 570トークン × 106件。1セッションあたり約300トークン（文脈の2〜4%）
- 損 = 21% の確率で読み直し1往復（約3〜5秒）

**ほぼ引き分け。** しかも上限を下げれば失う情報が増えるので、読み直し率は21%より上がる。
調整済みの既定値を、引き分けの証拠で動かす理由が無い。**変更しない。**

## まとめ

3つのうち効いたのは1つだけ。それも「コードで削る」話ではなく
「**長くなったことを持ち主に見せる**」話だった。

qwc の文脈まわりは既に良い状態にある（キャッシュ再利用率 96.4%、
再処理トークン数 ≒ 増分）。残っていた取り分は小さい。

「遅い」の実体は無駄ではなく、**26B モデルのこの機械での素の速度**（24〜37 tok/s）と、
**会話が伸びたときの 35% の劣化**。前者は変えられない。後者は切れば戻る。
